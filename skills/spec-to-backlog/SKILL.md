# Разбор документа в бэклог

Три фазы, каждая заканчивается проверяемым результатом. Между фазами не проскакивать:
пропуск второй даёт бэклог, который потом переделывают руками.

## Фаза 1. Разбор источника

Прочитай документ целиком. Не пересказывай его в трекер дословно — **вытащи структуру**.

- Верхний уровень документа обычно ложится на **эпики**, пункты внутри — на **истории**.
- Не изобретай третий уровень, которого в документе нет. Задачи внутри историй заводи,
  только если разбиение есть в источнике или человек прямо попросил.
- **Формулировки сохраняй авторские.** Опечатки и корявые обороты — это текст человека,
  а не повод для редактуры. Правь только там, где смысл теряется, и **скажи, что поправил**.
- Незнакомые сокращения и термины оставляй как есть. Догадка в названии задачи хуже,
  чем непонятное слово: непонятное спросят, а догадку примут за факт.

Выдели отдельно то, что **не относится к этому проекту**. Документ часто содержит несколько
направлений; свалить всё в один проект — самая частая ошибка разбора.

## Фаза 2. План файлом и опрос

Собери план в JSON и положи рядом с источником:

```json
{
  "project": "<слаг>",
  "epics": [
    { "subject": "Название эпика",
      "stories": [
        { "subject": "Название истории",
          "description": "Подробности из документа",
          "assign": "Фамилия",
          "status": "Backlog",
          "tasks": [ { "subject": "Шаг" } ] }
      ] }
  ],
  "stories": [ ]
}
```

`stories` верхнего уровня — для историй без эпика. `description`, `assign`, `status`, `tasks`
необязательны.

Покажи, что получится, **не записывая ничего**:

```
taiga plan <файл>
```

Команда выведет дерево с пометками «создать» и «есть #N».

Теперь **опрос — и только по пробелам**. Спрашивай:

- куда отнести пункты, не подходящие проекту;
- кто исполнитель, если в документе имя есть, но неоднозначно;
- нужен ли третий уровень, если документ его не даёт, а объём просит;
- решения, которых в источнике нет и вывести их нельзя.

Не спрашивай: то, что явно написано в документе; то, что можно спросить у трекера
(`taiga projects`, список статусов в ошибке `taiga mv`); необязательные поля — их оставляют
пустыми и упоминают в отчёте.

Опрос, который спрашивает всё, перестают читать — и блокирующий вопрос проходит вместе
с остальными.

## Фаза 3. Применение

Только после того, как человек подтвердил план:

```
taiga apply <файл>
```

Команда покажет превью ещё раз и спросит согласия. Она **идемпотентна**: существующее по
названию пропускается, создаётся только недостающее, ничего не переписывается.

Отсюда правило повторного прогона: **не трогать то, что люди уточнили руками.** Если история
в трекере переименована, повторный прогон заведёт её заново как новую — поэтому перед
повторным применением сверь план с текущим состоянием и доложи расхождения человеку,
а не выравнивай их сам.

## Отчёт

Коротко: сколько эпиков, историй и задач создано, сколько пропущено как существующие, что
не удалось и почему. Отдельно — список того, что ты **не завёл** и по какой причине:
пункты не из этого проекта, непонятные места, поля оставленные пустыми.

## Границы

- Проект и спринты не создавать: это решение человека, а не разбора.
- Участников в проект не добавлять: успешный ответ означает отправленное письмо.
- Ничего не удалять.
