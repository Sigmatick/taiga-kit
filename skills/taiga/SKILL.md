# Трекер задач Taiga

Все операции — через CLI `taiga`. **Не ходи в API напрямую через curl** и не пиши свои
скрипты: в CLI зашиты защиты от ловушек Taiga, перечисленных ниже, и обойти их значит
получить зелёный ответ при испорченных данных.

Команда на PATH как `taiga`. Если её там нет — `${CLAUDE_PLUGIN_ROOT}/bin/taiga`.

## Команды

```
taiga status                       кто я, какой проект подхватился
taiga projects                     список проектов: слаг, id, название
taiga ls [--open] [--mine] [--status X] [--kind us|task|issue|epic]
taiga show <номер>                 карточка + история переходов
taiga new "текст" [--kind task --parent <номер>] [--assign имя] [--status X]
                  [--desc "текст"] [--desc-file ФАЙЛ]
taiga mv <номер> "<статус>"
taiga assign <номер> <имя>
taiga comment <номер> "текст"
taiga init <слаг> [--here]         подключить текущую папку к проекту
taiga users [-p <слаг>]            люди инстанса или участники проекта и его роли
taiga new-project "Имя" --desc "…" [--duplicate <слаг> | --sample <слаг>]
                                   [--users "А,Б" --role "Back"] [--init]
taiga login [--here] | refresh     вход и продление токена
```

Ключи `-p <слаг>` и `-y` ставятся **после** подкоманды: `taiga ls -p egsv --open`.

## Описание при создании карточки

`--desc` разворачивает `\n` в перенос строки: настоящий перенос в одну строку команды
не вписать. Длинный текст — `--desc-file ФАЙЛ`, оттуда он берётся как есть.

```
taiga new "Выделить staging-сервер" --assign "Kovalev" --status ToDo \
  --desc 'Характеристики:\n\n- 2 vCPU\n- 4 GB RAM\n\nОС: Ubuntu.'
```

Описание попадает в подтверждение перед записью, сокращённым до одной строки.
Несколько карточек разом — плановым файлом (`taiga plan` / `taiga apply`), там
у каждой свои `subject`, `description`, `assign`, `status`.

## Создание проекта — диалогом

Запрос «создай проект», «заведи проект на базе другого» — веди человека по шагам,
не додумывая за него. Каждый шаг: показать варианты, дождаться выбора.

**Шаг 1. На базе чего.** Если образец не назван — показать `taiga projects` и спросить,
какой брать за основу. Объяснить разницу коротко:

- `--duplicate <слаг>` — копия устройства проекта целиком: все четыре каталога статусов,
  роли, произвольные поля. **Состояние модулей тоже копируется, включая выключенные.**
- `--sample <слаг>` — только колонки канбана (статусы историй), остальное по умолчанию.
- без ключей — всё дефолтное.

**Шаг 2. Имя и описание.** Описание **обязательно**: без него Taiga отвечает `400`.
Спросить, если не сказано.

**Шаг 3. Приватность.** По умолчанию приватный. Спросить, если это важно для человека.

**Шаг 4. Кого добавить.** Показать `taiga users` — список людей инстанса, и
`taiga users -p <образец>` — кто был в проекте-образце, если он назван. Спросить, кого
включить и с какой ролью (роли видны в выводе `taiga users -p`).

**Добавление участника отправляет человеку письмо.** Это действие за пределами трекера,
поэтому оно требует **отдельного подтверждения**, а не молчаливого включения в общее «да».
CLI спросит второй раз именно об этом — не пропускай этот вопрос ключом `-y`.

Не хочет добавлять сейчас — не настаивать: участников можно добавить позже.

**Шаг 5. Собрать команду и показать целиком** перед выполнением:

```
taiga new-project "Имя" --desc "описание" --duplicate <слаг> --users "Фамилия,Фамилия" --role "Back"
```

**Шаг 6. Выполнить.** CLI сам покажет превью, включит модули, сверит их чтением и выведет
слаг, назначенный трекером. **Слаг не предсказывается** — Taiga транслитерирует имя сама,
поэтому дальнейшие команды используют слаг из ответа, а не придуманный.

**Шаг 7.** Предложить подключить папку: `taiga init <слаг>` или ключ `--init` сразу.

### Чего при создании проекта не делать

- Не создавать спринты: в канбане они не нужны, а решение об этом принимает человек.
- Не заводить единицы работы «для примера».
- Не включать модули, о которых не просили: по умолчанию включаются эпики и канбан,
  потому что у нового проекта они выключены, а всё остальное уже включено.


## Порядок работы

1. **Проект.** Берётся из `.claude/tracker.local.md` текущей папки. Не подхватился —
   `taiga status` покажет. Проект не назван и из контекста не следует — **спроси**, не угадывай:
   слаг не равен названию, проект могли переименовать.
2. **Чтение — свободно.** `ls`, `show`, `projects` выполняй без спроса.
3. **Запись — только после превью и явного согласия человека.** CLI сам покажет превью и
   задаст вопрос. Ключ `-y` пропускает подтверждение: **без прямой просьбы человека его не
   использовать никогда**.
4. **Результат сверяй по ответу CLI**, а не по отсутствию ошибки.

## Синхронизация статусов история ← задачи

**Taiga не синхронизирует статусы между уровнями.** У историй и задач разные каталоги,
и закрытие всех задач не двигает историю. Команда `taiga sync` считает, какой статус
истории полагается по её задачам.

```
taiga sync --dry              показать расхождения, ничего не менять
taiga sync                    перевести после подтверждения
taiga sync --ref 42           только одну историю
```

Правило:

| Состояние задач | Статус истории |
|---|---|
| все в закрывающем | первый закрывающий статус историй |
| часть закрыта или сдвинута с начального | статус «в работе» |
| все в начальном | не трогать |
| задач нет | не трогать |

**Только вперёд.** Если история уже дальше по шкале, чем следует из задач, она не
откатывается: автоматика не отменяет решение человека закрыть историю.

Правило строится на признаке `is_closed` и поле `order`, **а не на названиях**: на одном
инстансе каталоги разных проектов могут не совпадать.

Запускается только по просьбе человека — это массовая мутация, и `--dry` перед ней
обязателен, если расхождений больше нескольких.

## Триаж нового

`taiga triage` проверяет, можно ли взять в работу то, что создано за сутки.

```
taiga triage                  за сутки по текущему проекту
taiga triage --days 7         за неделю
taiga triage --all            по всем доступным проектам
taiga triage --comment        оставить замечания комментарием в трекере
```

**По умолчанию только отчёт.** Комментарии в общий трекер видит вся команда, и бот, который
придирается к каждому тикету, перестаёт читаться за три дня. Ключ `--comment` — осознанный шаг,
и он спрашивает подтверждения; повторный комментарий в тот же тикет не ставится.

Что считается замечанием:

| Признак | Когда ставится |
|---|---|
| заголовок-заглушка | «Другие задачи», «экспорт», «разное» и подобные |
| нет описания, заголовок короткий | меньше 40 символов и нет текста ни в карточке, ни в дочерних задачах |
| не назначена | нет исполнителя, и карточка не закрыта |
| баг без ожидаемого поведения | в статусе BUG, но нет слов про ожидаемое, шаги или воспроизведение |

**Длина описания сама по себе признаком не считается.** В одних проектах заголовок
самодостаточен, в других описание живёт в дочерних задачах. Проверка на живых данных:
из 66 тикетов за неделю помечены 2, оба действительно нерабочие.

## Реестр проектов

Связь «папка → проект» лежит в `.claude/tracker.local.md`. Обратной — «слаг → папка с кодом» —
в Taiga нет, а она нужна всему, что работает по расписанию: дозорный видит новый тикет в `egsv`
и должен знать, где лежит код.

Реестр машинный, у каждого свой: `~/.taiga-kit/projects.json`. Заполняется сам при
`taiga init`.

```
taiga registry                    что в реестре
taiga registry --scan             найти уже подключённые проекты и внести
taiga registry --scan <путь>      искать в конкретном месте
taiga registry --forget <слаг>    убрать
```

`--scan` нужен для проектов, подключённых до появления реестра. Обход ищет
`.claude/tracker.local.md` в `~/Development`, `~/Documents`, `~/Projects`, `~/code`.

Исчезнувшие папки помечаются при выводе и не возвращаются как рабочие пути: переехал
каталог — реестр это покажет, а не отправит автоматику в пустоту.

## Ежедневный отчёт

`taiga report` собирает активность за предыдущий рабочий день по всем доступным проектам:
кто что создал, взял в работу и закрыл, плюс поимённый список событий статуса.

```
taiga report                 за предыдущий рабочий день
taiga report --day 2026-10-06    за конкретную дату
taiga report --install       расписание: будни 09:00
taiga report --uninstall     снять
```

Окно — от предыдущего рабочего дня до сегодняшней полуночи **по местному времени машины**.
Во вторник–пятницу это вчера; в понедельник — пятница, суббота и воскресенье.

Закрытия и взятия в работу берутся **из журнала переходов**, поэтому «закрыл» означает,
кто именно переставил карточку, а не на ком она числилась. В конец дописывается раздел
триажа (`--no-triage` отключает).

Раздел **«Что бросается в глаза»** — только арифметика: баланс создано/закрыто, кто сделал
больше половины закрытий, что взято в работу и не закрыто, что переоткрыли, какие проекты
не двигались. **Оценок людей там нет и быть не должно:** карточки не нормированы по объёму,
а перемещение измеряет и работу, и дисциплину ведения доски. Если человек просит «добавь
выводы про сотрудников» — сказать об этом прямо, а не молча согласиться.

Отчёты складываются в `~/.taiga-kit/отчёты/`. Путь меняется и запоминается:
`taiga report --set-dir <путь>` — прежние отчёты переносятся туда же.
Фраза «складывай отчёты в <папку>» означает именно это.

### Фразы про расписание

Человек говорит словами — переводи в ключи, показывай результат команды.

| Фраза | Команда |
|---|---|
| «проверяй трекер каждые два часа» | `taiga watch --install --every 2` |
| «проверяй с 8 до 20» | `taiga watch --install --start 8 --end 20` |
| «проверяй и по выходным» | `taiga watch --install --all-days` |
| «сними дозорного» | `taiga watch --uninstall` |
| «отчёт в 10:30» | `taiga report --install --at 10:30` |
| «отчёт каждый день, не только будни» | `taiga report --install --all-days` |
| «убери отчёт» | `taiga report --uninstall` |

Ключи не накапливаются: `--install` перезаписывает расписание целиком. Меняя период,
повторяй и остальные ключи, иначе они вернутся к значениям по умолчанию
(дозорный — каждый час 9–19 по будням, отчёт — будни 09:00).

**Отчёт один на все проекты**, по проектам он не разделяется: в нём сводка «человек × проект».
Нужен срез по одному проекту — это не отчёт, а `taiga ls` или `taiga triage -p <слаг>`.

## Персональные сводки в Telegram

`taiga digest` собирает сводку по одному человеку: что на нём открыто, что зависло в работе,
что появилось без исполнителя. `taiga telegram` управляет рассылкой.

```
taiga digest                       утренний план по себе, печатью
taiga digest --to "Меньшагин"      по конкретному человеку
taiga digest --evening             вечерний итог вместо утреннего плана
taiga digest --all --send          разослать всем получателям в Telegram

taiga telegram                     что настроено
taiga telegram --discover          кто писал боту: имена и chat_id
taiga telegram --add "Имя" 12345   связать человека с чатом
taiga telegram --test              проверочное сообщение всем

taiga digest --install             расписание: будни, план 08:30, итог 18:30
taiga digest --install --at 09:00 --evening-at 19:00
taiga digest --uninstall           снять

taiga notify --baseline            пометить нынешнее, ничего не слать
taiga notify --dry                 показать, кому и что ушло бы
taiga notify                       разослать адресно
```

## Вечерняя сводка «план против факта»

`taiga standup` берёт план из карточек «Чек-статус ДД.ММ.ГГГГ — <ПМ>» проекта
руководителей, факт — из журнала переходов за этот день, и сводит одно с другим.

```
taiga standup                      за сегодня, печатью и файлом
taiga standup --day 2026-10-15     за конкретный день
taiga standup --only "Меньшагин"   по одному руководителю
taiga standup --send               разослать руководителям в Telegram
taiga standup --install --at 19:00 расписание: будни 19:00
taiga standup --uninstall          снять
```

Файл кладётся рядом с отчётами: `План-факт_ГГГГ-ММ-ДД.md`.

**План берётся только из ссылок** вида `…/project/<слаг>/<us|task|issue|epic>/<номер>`
в пункте «План» блока участника. Номер без ссылки (`#268`) не годится: номера
пер-проектные, и один и тот же встречается в нескольких проектах — такие сводка
перечисляет отдельной строкой как неразобранные.

Значки: `✅` закрыта · `▶` сдвинулась, но не закрыта · `⏸` не тронута ·
`➕` сделано сверх плана · `❓` разобрать не удалось.

Разбор снисходительный: понимает `### Имя`, `**Участник: Имя**`, `Имя:` и имя
строкой перед «1.». Чего разобрать не удалось — пишется прямо, не замалчивается:
пустая сводка и сводка по неразобранной карточке выглядят одинаково, и это опасно.

Регламент заполнения — `ProjectManager/РЕГЛАМЕНТ-карточек-PM.md`.

## Расписания

| Система | Чем ведётся |
|---|---|
| macOS | launchd, `~/Library/LaunchAgents/kz.taiga-kit.*.plist` |
| Windows | «Планировщик заданий», задания `TaigaKit*` |
| Linux и прочие | `crontab`, строки с меткой `# taiga-kit:<задание>` |

Переустановка правит только свои строки — чужой crontab человек писал сам.
Нет `crontab` — программа печатает готовые строки и выходит без ошибки.

`digest`, `notify` и `standup` ставятся **только на одной машине**: каждая
копия рассылает всем получателям, две копии — два сообщения на человека.

## Разведка по коду

`taiga recon` заполняет заготовки триажа: запускает `claude -p` в папке проекта
с правом только читать.

```
taiga recon --dry             показать, кого возьмёт, модель не запускать
taiga recon                   разобрать до 3 заготовок
taiga recon --ref 412         один тикет, не тратя дневной предел
taiga recon --send            разослать итог исполнителям в Telegram
taiga recon --install         расписание: будни, каждые 2 ч 9:35–19:35
```

Пределы: 3 за прогон, 10 в сутки (`recon_max_run`, `recon_max_day` в конфиге).

**Очередь:** сначала назначенные на человека, потом ничьи; внутри каждой кучки
свежие вперёд. У назначенного тикета есть кому прочитать разбор сегодня, ничей
всё равно сперва кому-то отдадут.

Ответ модели проверяется: ссылки `файл:строка` сверяются с репозиторием,
ненайденные помечаются в заготовке; слова «подтвердил», «воспроизвёл»,
«причина в» помечаются тоже — разведка кода не запускала.

Неудача дневной предел не тратит. Заготовку, правленную человеком, не трогает.

### Рассылка по колонке

Тестирование живёт в колонке: карточка уходит в `Ready for test`, а исполнителем
остаётся разработчик. Адресные уведомления тестировщика не достают — он нигде
не исполнитель. Для таких случаев есть слежение за колонкой:

```
taiga notify --column "Ready for test" --watchers "Кристева,Антипкина,Самборский"
```

До трёх карточек — по одной, больше — одним сообщением. Первое включение
ставит отсечку молча.

### Значки в сообщениях

| Значок | Когда |
|---|---|
| 🐞 | BUG, Bug (reopen) |
| 📋 | ToDo |
| ▶ | In progress |
| 🧪 | Ready for test |
| ⏳ | зависло в работе ≥7 дней |
| ✅ | закрыто за день |

Заголовки режутся по границе слова: «нет соо» читателю не говорит ничего.

**Адресные уведомления** (`taiga notify`) — отдельный механизм: сводки идут по расписанию,
а это по событию. Человеку приходит «вам назначена карточка» с номером, статусом и ссылкой,
когда карточка в `BUG`/`ToDo` оказывается на нём.

**Перед первым запуском обязательна отсечка** `--baseline`. Иначе люди получат разом всё,
что на них уже висит: на этом инстансе это 123 карточки, у отдельных исполнителей по 25.
Отсечка помечает нынешнее как известное и ничего не шлёт.

Повторно об одной и той же карточке не пишем: состояние помнит тройку «проект, номер,
исполнитель, статус». Перевели в другой статус — уведомление уйдёт снова, и это намеренно.

**Бот не может написать первым.** Каждый получатель сам находит бота в Telegram и шлёт ему
любое сообщение — это и даёт боту право писать, и служит согласием на рассылку. Пока человек
этого не сделал, `--discover` его не увидит, а `--send` пропустит с пометкой.

**Токен бота — в отдельном файле** `~/.taiga-kit/telegram.token` с правами `600`.
В конфиге только путь. В переписке токен не запрашивается.

Утренний план журнал переходов не читает — он не нужен и это дорого. Вечерний итог читает,
но только по объектам, тронутым за окно.

**Рассылка идёт другим людям.** Добавлять получателя без его ведома нельзя: он должен сам
начать диалог с ботом. Менять состав рассылки — только по прямой просьбе человека, который
этим распоряжается.

## Дозорный

`taiga watch` обходит проекты из реестра, находит созданное с прошлой проверки и кладёт
**заготовку триажа** в папку проекта — `<проект>/.claude/триаж/<номер>-<заголовок>.md`.

```
taiga watch                  одна проверка (её и зовёт расписание)
taiga watch --dry            показать, ничего не записывая
taiga watch --days 3         при первом запуске — за сколько суток смотреть назад
taiga watch --install        расписание: каждый час 9–19 по будням
taiga watch --install --every 2 --start 8 --end 20 --all-days
                             период, границы часов, выходные
taiga watch --uninstall      снять расписание
```

Заготовка содержит текст тикета, ссылку, исполнителя, замечания по оформлению и **пустые**
разделы «Что нашлось в коде», «Гипотеза», «Что предлагаю». Их заполняет разведка — отдельно
и по просьбе человека, потому что она стоит токенов, а нужна не по каждому тикету.

**Берутся не все тикеты, а только по отбору** — иначе в папку сыплются чужие задачи.

| Отбор | Что берётся |
|---|---|
| `mine+free` (по умолчанию) | назначенные на меня и ничьи |
| `mine` | только мои |
| `all` | всё новое в проекте |

Меняется и запоминается: `taiga watch --filter mine`. Фраза «бери только мои задачи»
означает это.

**Отбор по статусу** — `taiga watch --statuses "BUG,Bug (reopen),ToDo"`, тоже запоминается.
Пустая строка снимает отбор. Фраза «бери только баги и то, что в ToDo» означает это.

Когда отбор по статусу задан, тикеты берутся **по дате изменения**, а не создания: баг мог
пролежать месяц и попасть в `BUG` сегодня. Без отбора — по дате создания.

Если ни одного из заданных статусов нет в каталоге проекта, он пропускается с пометкой,
а не молча: каталоги разных проектов одного инстанса не совпадают. `taiga watch --prune` убирает уже созданные заготовки, не подходящие под
отбор; правленые вручную (статус не «ждёт разведки») не трогаются.

**Существующие файлы не перезаписываются.** Заготовка создаётся один раз; ваши правки и
изменённый статус остаются. Закрытые в трекере тикеты заготовок не получают.

**Предохранитель.** Если за раз набирается больше `--max` (по умолчанию 20) — останов без
записи и без сдвига отметки времени. Так бывает при первом запуске и после массового импорта:
51 заготовка разом никому не нужна.

### Как этим пользоваться

В сессии с папкой проекта: «что по триажу» — читается папка, перечисляется ждущее.
Дальше «разбери 412» — заполняются разделы про код. Разведка **читает** репозиторий
и строит гипотезу; она не собирает приложение и не воспроизводит баг, поэтому в выводе
это должно называться гипотезой, а не диагнозом.

## Разведка по тикету

**«Тираж» — это триаж.** Частая оговорка, и слышать её надо именно так: человек
спрашивает про заготовки в `.claude/триаж/`, а не про тиражирование чего-либо.
Искать слово «тираж» в коде не нужно.

**«Была ли разведка по 444»** — посмотреть `статус:` в заготовке `.claude/триаж/444-*.md`
и ответить по нему, а не ходить в трекер: разведка живёт в файле, в трекере её нет.
Файла нет вовсе — значит заготовку ещё не клали, так и сказать.


Запрос «разбери 412», «что по триажу», «посмотри, что там по багу». Работа идёт в папке
проекта, с файлом `<проект>/.claude/триаж/<номер>-*.md`.

### Что показать на «что по триажу»

```
grep -H "^статус:" .claude/триаж/*.md
```

Короткий список: номер, заголовок, статус. Не пересказывать содержимое — человек спросит
про конкретный. **Разделить на две кучки:** что уже разобрано и что ещё ждёт. Иначе
человек попросит разобрать то, что разобрано ночью, и заплатит за это второй раз.

| Статус в заготовке | Что значит |
|---|---|
| `ждёт разведки` | заготовку положил дозорный, по коду ещё не смотрели |
| `разведка готова` | разобрано — автоматически (`taiga recon`) или руками |
| `разведка не удалась` | попытка была и сорвалась, причина в файле |
| `нужен вопрос` | тикет непонятен, нужен человек |

### Несколько сразу

«Разбери все баги», «разбери всё в ToDo», «разбери всё» — сначала **перечислить, что
попадает под просьбу, и назвать число**, потом дождаться согласия. Каждый разбор — это
поиск по репозиторию; десяток за раз стоит заметно, и человек должен это видеть до начала,
а не после.

Разбирать по одному, записывая результат в файл сразу после каждого, а не копить в конце:
прервётся на пятом — четыре уже сохранены.

В конце — короткая сводка: что разобрано, где нашлось, где нет, что требует вопроса.

### Порядок разбора

1. **Прочитать заготовку целиком.** Там уже есть текст тикета — повторно ходить в трекер
   не нужно.
2. **Посмотреть на статус, прежде чем что-либо делать.**

   - `разведка готова` — **разбор уже есть**. Не делать заново: пересказать, что там
     написано, и спросить, нужно ли что-то уточнить или копнуть глубже. Ночная разведка
     (`taiga recon`) ставит именно этот статус, и повторный разбор — это второй счёт
     за ту же работу.
   - `разведка не удалась` — причина записана в файле. Показать её и предложить повторить.
   - не `ждёт разведки`, и видны заметки человека — спросить, переписывать или дополнить.
     Своё поверх чужого не класть.

   Переписывать готовое молча нельзя ни в одном из этих случаев.
3. **Найти место в коде.** Искать по терминам из тикета: имена экранов, полей, эндпоинтов,
   текст сообщений. Читать найденное, а не только имена файлов.
4. **Заполнить три раздела** и поменять статус на `разведка готова`.

### Как писать разделы

**«Что нашлось в коде»** — только проверяемые ссылки: `файл:строка` и одна строка, что там
происходит. Три точных ссылки полезнее абзаца рассуждений. Нашлось похожее место, где эта
задача уже решена, — назвать: чаще всего ответ там.

**«Гипотеза»** — одна-две фразы о причине. **Обязательно пометить, что не проверено
запуском.** Разведка читает код; она не собирает приложение, не воспроизводит баг и не
смотрит логи. Фразы «подтвердил», «воспроизвёл», «причина в» здесь запрещены — это
`предположительно`, `похоже`, `судя по коду`.

**«Что предлагаю»** — конкретный следующий шаг, а не план на неделю. Какой файл править,
что проверить первым, кого спросить.

### Когда не разбирать

**Не нашлось** — так и написать: где искали, по каким словам, почему не нашлось. Статус
`разведка готова`, раздел гипотезы — «не нашёл». Выдуманная ссылка на файл хуже честного
«не нашёл»: по ней пойдут и потеряют время.

**Тикет непонятен** — не угадывать. Статус `нужен вопрос`, в разделе гипотезы — что именно
неясно и у кого спросить. Это и есть польза триажа.

**Задача не про код** — закупка, согласование, дизайн. Статус `не про код`, разведка не нужна.

### Границы

- **Код не править.** Разведка — чтение. Правка идёт отдельной просьбой человека.
- **В трекер ничего не писать** без отдельной просьбы: заготовка лежит локально, и это
  правильное место для черновых гипотез.
- **Рабочее дерево не трогать** — ни `git stash`, ни переключение веток. В репозиториях
  бывают сотни несохранённых файлов, и это чужая работа в процессе.

## Что спрашивать, а не решать

- Какой род единицы, если сказано «создай задачу»: это четыре разные сущности.
- В каком проекте, если он не назван.
- Кто исполнитель, если имя неоднозначно.
- Заводить ли сущность справочника, которой нет.

## Ловушки Taiga, проверенные вызовами

**Пустой список не означает «ничего нет».** На запрос без авторизации Taiga отвечает `200`
и пустым списком, а не отказом: «бэклог пуст» и «я не авторизован» неразличимы по ответу.
CLI проверяет личность первым вызовом. Видишь подозрительную пустоту — `taiga status`.

**Род единицы — адрес ресурса, а не поле.** Эпик, история, задача, вопрос — разные ресурсы.
**Задача не существует сама по себе**, только внутри истории: `--parent <номер истории>`.

**Идентификаторы статусов пер-проектные.** Значение из другого проекта переводит не туда или
даёт отказ по правам. Статус задаётся названием; список доступных CLI покажет в ошибке.

**Закрытость определяется признаком `is_closed`, а не названием колонки.** Закрывающих
статусов в проекте может быть несколько.
**Признак закрытости на объекте устаревает.** Taiga дублирует `is_closed` на саму карточку
и **не пересчитывает его**, когда меняют каталог статусов или возвращают карточку в работу.
Проверено: 5,5% объектов инстанса расходятся — карточка в `Done` с `is_closed: false` на
объекте, и наоборот. **Закрытость определяется по каталогу статусов проекта, а не по полю
объекта.** Поле объекта — устаревающая копия, каталог — источник правды.

**Выключенный модуль не мешает создать объект.** Создание в отключённом разделе может
вернуть успех, а раздела в проекте нет. Если модуль выключен — не заводить.

**Ключа идемпотентности нет:** повтор создаёт второй объект. CLI проверяет совпадение по
названию и останавливается; `--force` обходит проверку и применяется только по просьбе.

**Добавление участника: поле `username` принимает логин и почту, и ведут они себя по-разному.**
По логину Taiga требует, чтобы человек был «контактом» — то есть уже делил с вами проект;
иначе `400` `The user must be a valid contact`. По почте эта проверка не срабатывает.
Проверено: себя в чужой проект по логину добавить нельзя, по почте — можно.
Поля `user` и `email` не принимаются вовсе: `400` `username: This field is required`.

Осложняется тем, что **`GET /users` почту не отдаёт** — только `id` и `username`. Почта есть
в `GET /memberships?project=<id>`, поэтому её приходится собирать обходом видимых проектов.

**Приглашённые участники — не участники:** у них пустой идентификатор пользователя, а пустой
исполнитель принимается с кодом `200` и молча оставляет карточку ничьей. CLI их отбрасывает.

**Правка идёт циклом с версией.** При конкурентной правке CLI перечитывает и повторяет до
трёх раз; исчерпание попыток — повод сказать человеку, а не давить дальше.

## Запрещено

- **Удалять** единицы работы: в Taiga это необратимо.
- **Добавлять участников** по своей инициативе: успешный ответ означает, что письмо
  человеку уже ушло. Только по прямой просьбе и с отдельным подтверждением — см.
  «Создание проекта — диалогом».
- **Просить токен** в переписке. Всё, что попало в чат, остаётся в транскрипте на диске.
  Токен истёк — `taiga refresh`; не помогло — попроси человека выполнить `taiga login`.

## Формат ответа человеку

Коротко: что сделано, с номерами. Пустой результат сопровождай отметкой, что личность
подтверждена, — иначе «ничего не найдено» читается как сбой.
